# 协同编辑器

一个基于 DOM 渲染的块状编辑器。多个浏览器同时打开时，一个人输入的内容会实时出现在其他人的屏幕上。

这是为一道面试作业题做的，本文覆盖七个部分：怎么运行、用了什么技术、数据结构怎么设计、协同怎么实现、遇到了什么问题、还有哪些没完成、如果继续开发准备怎么优化。

## 一、怎么运行

### 本地开发

```bash
npm install
npm run dev
```

打开 <http://localhost:5173>，注册一个账号，然后开第二个标签页登录另一个账号。

### Docker

```bash
cp .env.example .env      # 改掉里面的管理员账号密码
docker compose up --build
```

打开 <http://localhost>。nginx 在 80 端口，把 `/api` 和 `/ws` 转给 3000 端口的服务端，数据库放在 `collab-data` 卷上。

| 命令 | 作用 |
| --- | --- |
| `npm run dev` | 同时起服务端（3000）和前端（5173） |
| `npm test` | 跑测试，共 251 个 |
| `npm run typecheck` | 三个包一起做类型检查 |
| `npm run build` | 生产构建 |
| `npm start` | 跑构建好的版本 |

## 二、用了什么技术

原生 TypeScript + Vite + Node + `ws` + Vitest。**没有引入任何运行时依赖，也没有用编辑器框架。**

不用编辑器框架是故意的：这道题真正有意思的地方是**协同那一层**，不是富文本渲染。套一个 ProseMirror 进来会把重点藏起来。

代码分成三个包：

- `shared/` —— 操作的定义和通信协议
- `server/` —— 文档状态、WebSocket 服务、账号与登录
- `client/` —— DOM 编辑器、连接管理、登录界面

## 三、数据结构怎么设计

一个文档就是一串**块**，每个块是 `{ 编号, 文字 }`。

**关键决定：操作按「块的编号」定位，而不是按「一整条字符串里的第几个字」定位。**

如果整个文档是一条长字符串，你在中间改一个字，后面所有位置都会平移，每次并发编辑都变成"重新编号"的问题。分成块之后，编号是稳定的，插入、拆分、合并都只是一次数组操作，而且别人说"在第 7 块的偏移 5 插入"，**不需要知道文档的其他部分长什么样**。

几个细节：

- **操作里存的是「意图」，不是「结果」。** 存的是"我要在第 5 位插入 World"，不是"这一块现在应该是 Hello World"。存结果的话，两个人同时改会互相覆盖；存意图，服务端才有机会把两条都保留下来。
- **位置一律按 UTF-16 单位算。** 协议、光标计算、光标恢复三处用的是同一个单位。emoji 占两个单位，所以算文本差异时会特意避开中间，防止把一个 emoji 从中间切开传出去。
- **暂时不做索引优化。** 块的数量上限是 500，线性扫描足够快；换成字典又要处理拆分和合并时的失效，这个规模下不划算。
- **不用树，不用 rope。** 树是为了嵌套（Notion 那种），rope 是为了超长单文档，两个都不是这个场景要解决的问题。

## 四、协同怎么实现

**服务端是唯一的校验者，也是唯一的排序者。**

1. 客户端**先本地应用**自己的修改，所以打字不等网络；然后把操作打包成一条事务发出去。
2. 服务端拿一份**草稿**把每个操作试跑一遍，**全过才真正应用**。这就是事务的原子性，也是为什么"回车拆分 + 往新块里插入"这一串操作能合法地放在同一条事务里。
3. 成功后版本号加一，把这条事务**广播给所有人，包括发送者自己**。发给发送者是为了只留一条代码路径，而且这个回声正好是将来挂"确认回执"的地方。客户端认出自己的回声就丢掉，因为本地已经应用过了。
4. 失败时服务端回一个**错误**加一份**快照**。这两件事是配套的：只回错误，客户端知道自己错了但不知道现在该是什么；只回快照，客户端不知道自己错在哪。快照是唯一能纠正状态的东西，所以被拒绝的修改会**看得见地缩回去**，而不是悄悄跑偏。
5. 客户端收到版本号不是"自己的加一"的消息，就主动要一份快照，而不是猜。**这个判断之所以成立，是因为有"一条事务恰好加一个版本"这条规则。**

### 为什么不用 OT / CRDT

服务端已经是唯一的排序者了，从这个位置做服务端 OT，比从头做一个 CRDT 近得多。CRDT 的好处是不需要中心排序、离线也能合并，代价是数据结构和删除逻辑复杂很多。

更实际的理由：**半成品 OT 比看得见的分歧更糟。** 分歧至少能被快照纠正回来，一个写错的变换会**静默地**把文档改坏。

## 五、遇到了什么问题

这一节是这一周里最有价值的部分。

- **重建界面会摧毁光标。** 别人拆分或合并了块，块的数量变了，就得整块重建 DOM，而重建会把正在打字的人的光标弄丢。解决办法是重建前先记下"哪个块的哪个位置"，重建后恢复，并加一个判断让本地的回车操作不被覆盖。
- **`contenteditable` 会产生嵌套标签。** 所有读取都走 `textContent`，因为位置计算依赖"一个块内部是一个扁平的文本节点"。这也是粘贴用 `execCommand` 而不是直接插入节点的原因。
- **中文输入法要挡三道。** 输入时、按键时、以及一个记录"正在拼字"的集合。少一道，回车就会在拼字过程中把块切开。
- **离线时输入会静默丢失。** 连接没打开的时候，发送函数直接返回，但序号已经加一了。这是已知的洞，测试专门钉住了它。
- **密码加密算法的内存参数不够。** 每次调用都抛异常，因为它需要的比默认值多了 1.5MB。改成显式指定就好了，一次大约 58 毫秒。
- **网页服务器把接口请求当成了静态文件。** 登录失败会返回一个 200 加一段 HTML，前端解析不了，看起来像服务端崩了。加一条接口专用的转发规则就好了。
- **走 Cloudflare 时登录凭证永远拿不到安全标记。** Cloudflare 在它那边就把加密解掉了，网页服务器看到的永远是普通 http。解决办法是有上游信息就用上游的，没有才自己判断。
- **给界面加翻译标记时踩了一个坑。** 顶栏有三个小方框的内容是运行时才填的（比如用户名），如果给它们也加"统一翻译"的标记，**一切换语言，用户名就会被覆盖成"未登录"**。这个 bug 只有真的切一次语言才会现形，看代码是看不出来的。

## 六、还有哪些没完成

- **没有确认回执。** 客户端不知道自己发出去的东西成没成，只知道被拒绝的时候收到了错误。
- **断线重连很粗糙。** 每秒硬试一次，没有逐渐放慢；重连之后直接接受服务端的快照，**没发出去的本地修改会被无声丢弃**。
- **不幂等。** 序号和基础版本号在协议里传了，但服务端**两个都不看**。所以同一条事务重发会执行两次——这是**故意用测试钉住的**，不是漏掉了。修法是服务端按客户端记一个序号高水位，收到重复的就重新回一个回执而不是报错。注意这需要客户端编号能跨重连保持不变。
- **没有冲突合并。** 两个人改同一个块会各显示各的，而且没有任何提示。这是有意不做，而不是做了一半。
- **没有光标、没有锁、没有撤销重做。**
- **文档还在内存里。** 账号、登录记录、审计表都在硬盘上，但**文档本身不在**——重启服务端，文档就空了。持久化的正确单位是"每一次修改"，不是"最终结果"。
- **没有分房间。** 不管登没登录，所有人共用同一份文档。
- **注册是开放的。** 没有邀请码，找到这个站的人都能注册。
- **被删除的用户还挂在线上。** 他的下一次按键会被拒绝，但他的连接还开着，还能继续看文档。
- **限流只在内存里。** 单进程没问题，多开一个实例就不对了。
- **只有两种语言，而且不看浏览器语言设置。** 默认中文是写死的。

## 七、如果继续开发

按**依赖顺序**排，不是按重要性：

1. **稳定的会话令牌。** 现在每次重连客户端编号都会变，而这一件事挡住了后面四件：序号去重、光标归属、在线用户、锁的持有者。
2. **重发队列 + 服务端按序号去重。** 这就是面试题直接问的那两件事。
3. **客户端的位置修正。** 收到别人的操作时，先把它的位置按本地已经发生的变化调整一下。**因为服务端已经保证了顺序唯一，这里只需要处理"同一个块内部的位置偏移"这一种情况**——这是服务端当唯一排序者换来的好处。
4. **用操作日志做文档持久化。** 不是存快照。操作日志已经是服务端在盖章和排序的那个东西，存它才能既恢复文档、又保留追溯的能力。
5. **光标和在线用户。** 属于"感知"类功能，排在稳定身份之后。
6. **审计日志和管理后台。** 表已经建好并且加过索引了，但还没人往里写。写入点是**所有编辑唯一的那个漏斗**。
